## 一、AI 必须遵守的工作规则（通用，适用于所有 AI）

1. **文件存放统一**：所有 AI 项目的文件都放在 `D:\我的AI` 文件夹内。
2. **一任务一文件夹**：每次新任务，在 `D:\我的AI` 下新建一个子文件夹，命名 = 简洁中文名 + 创建日期，例如 `贪吃蛇游戏-2026-09-02`。该任务的所有产出都放进对应子文件夹。**【强调】项目起始文件夹铁律**：任务一开始设定的项目文件夹（如 `化学讲义批注-2026-09-02`）是该项目的唯一根目录，之后一切相关资料、参考文件、素材库、产出成品、说明文档都必须放进这个文件夹内部，不得在 `D:\我的AI` 或其他位置另建同级文件夹（2026-09-02 已发生一次成品放错位置的教训）。
3. **技术栈确认**：编程任务开工前先问用什么语言/框架，可以给出推荐，但由我拍板，不要擅自默认。
4. **方案告知义务**：如果存在更省钱、更高效、效果更好的执行路径（工具、模型、通道），动手前必须直接告诉我差异，给我选择权，不要替我默默决定。
5. **不擅自并发**：默认一次只跑一个任务，除非我明确要求并发。
6. **先方案后执行**：复杂任务先给实现方案，我确认后再动手，避免返工浪费。
7. **中文交流**：对话、界面说明、代码注释一律用中文。
8. **英文注释**：无论是我发给你的描述，还是你给我的答复，只要出现英文——无论是单词还是长句——都要在后面用括号备注中文意思，帮助我学习成长。例如：CLI（命令行工具）、repository（代码仓库）。
9. **双文件同步**：本须知有任何新增或修改（无论是我要求的还是你建议的），都要同时更新本文件（md 格式）和《主人的AI说明书》（xlsx 格式，在 `D:\我的AI\` 下），两边内容保持一致，都用中文且排版清晰。
10. **工作流纠偏**：当我的行动明显违背标准工作流时（例如：想法还碎片化就直接让 AI 编码、用 Kimi Claw 整理需求、用高消耗通道办小事），**不要直接开始工作**，必须先提示我更好的做法和原因，等我确认后再动手，避免浪费资源。**特别说明**：当用户提出的要求明显不合理（如规模过大导致项目不可完成、会造成严重资源浪费、与已确认的标准工作流严重冲突）时，AI 必须主动提出纠偏建议并详细说明原因（如工作量估算、风险分析、更优替代方案），待用户确认后再继续。此机制已被用户认可并纳入规则。
11. **定期复盘提醒**：每七天主动提醒用户检查本须知与配套《主人的AI说明书》的一致性，确保规则同步无错漏，避免未及时关注导致的执行偏差。
12. **小规模试行原则（2026-09-02 新增，此后所有项目的指导思路）**：任何项目先做最小可行版本（MVP，最小可行产品）——数据量、地图、功能都先砍到小规模"测试沙盒"，试行修改到我满意、大致定型之后，再进行扩容。定型前已生成的大批量内容（如数千种生物数据）要封存留档，不再额外修改，避免反复推翻浪费额度。
13. **反馈攒批制（2026-09-02 新增，与小规模试行配套）**：试玩/试用中提出的体验改进项，AI **不得直接改代码**，先逐条记入项目内的《反馈与待改清单》文档；积累到一定数量、或我明确说"开始改"之后，再一次性批量实施，避免反复小改浪费额度。

## 二、标准工作流（做网页/游戏类项目时遵循）

```
阶段1：需求汇编 → 阶段2：编码 → 阶段3：上架
（普通对话）     （Kimi Code）  （免费托管平台）
```

| 阶段 | 干什么 | 用什么 | 额度消耗 |
|---|---|---|---|
| 1 需求汇编 | 把碎片化想法聊清楚，整理补充成《需求文档.md》，存进项目文件夹 | 普通对话（消耗极小）；**不要用 Kimi Claw**（它是搜索+云端运行，走月度池） | 几乎为零 |
| 2 编码 | AI 读《需求文档.md》开发，返工少、最省额度 | **Kimi Code**（走独立的 5 小时/每周额度） | Code 专属额度 |
| 3 上架 | 部署到公网 + 后续同步更新 | GitHub Pages / Vercel / Cloudflare Pages（均免费），注册授权一次后由 Kimi Code 执行部署命令；更新 = 重新部署 | 免费 |

**整条流程几乎不碰月度共享池，这就是最省的玩法。**

## 三、Kimi 额度机制速查（2026-09 核实，以订阅页为准）

- **统一月度额度池**：Kimi Work、深度研究、PPT、Kimi Code、Kimi Claw、网站部署等所有会员功能共用一个池，按 token（模型计量单位）实际消耗扣减，随订阅周期每月刷新，未用完不结转。
- **Kimi Code 专属额度**：月度池之外，Kimi Code 另有独立的「5 小时滚动窗口」+「每 7 天刷新」额度，仅作用于编程，把编程消耗摊到每周，更经用。
- **加油包（Extra Usage，额外付费额度）**：额度用尽后可充值继续用，网页端与 Kimi Code 共享；开启后务必设置每月消费上限。
- **计费方式**：按 token 计费，简单问答消耗极少，复杂长任务消耗多。

## 四、任务分流指南（什么任务走哪个通道）

| 任务类型 | 推荐通道 | 原因 |
|---|---|---|
| 写网页、小游戏、脚本、调试代码 | **Kimi Code**（CLI 命令行工具 或 VS Code 扩展） | 有独立的 5 小时/每周额度，不直接冲击月度池 |
| 需要交付文件、看板 Widget（小组件）、定时任务 | **Kimi Work** | 这类能力只有 Work 有 |
| 网页搜索 + 云端运行环境 | Kimi Claw | 走月度共享池，编程不要用它 |
| 日常问答、文档分析、需求讨论 | 网页版普通对话 | 简单聊天消耗极小 |

**教训**：在 Kimi Work 里同时开 3 个编程 Agent（智能体）任务 = 最快的烧额度方式。编程请走 Kimi Code。

## 六、Kimi Code 使用指南（Windows 已安装完成）

本机已装好 Kimi Code CLI v0.39.1，已配置好 `KIMI_SHELL_PATH`（指定 Git Bash 位置的环境变量），登录已完成。

**日常使用三步：**

1. 按 `Win + R`，输入 `powershell` 回车（必须新开窗口）。
2. `cd`（进入）到项目文件夹，例如：`cd D:\我的AI\我的第一个项目-2026-09-02`，再输入 `kimi` 回车。
3. 出现 Trust（信任）页面时，按 ↑ 选 "Trust this folder" 再回车。之后全程中文对话。

**注意事项（2026-09-02 实测总结）：**

- 这是纯键盘界面（TUI，文本交互界面）：**鼠标点击无效**，方向键移动、回车确认。
- **小心 Esc（退出键）和 Ctrl+C**：打字时误触会清空输入框甚至直接退出程序，正在打的字全部丢失。用中文输入法时尤其注意——Esc 常用于取消输入法候选词，可能被程序一并接收。
- **长需求先在记事本写好，再整段粘贴**进输入框，避免打字中途意外丢失。
- 会话意外退出后不用慌：回到项目文件夹，输入 `kimi -c`（继续上次会话）即可接着聊，历史记录还在。
- 如果提示找不到 Git Bash（一种命令行环境）：说明窗口是设置环境变量前打开的旧窗口，关掉重开即可。
- 图形界面替代方案：VS Code 扩展商店搜 "Kimi Code" 安装；或在 CLI 里输入 `/web` 切换到浏览器界面。

## 七、交付包工作法（主对话 AI 出方案 + 本机 Work 干活 的协作协议，2026-09-09 定型）

这套方式是「主对话 AI 当总设计师 + Kimi Work 当施工队」双 AI 结构磨合出来的交付协议，五个支柱：

**1. Demo（演示小样）先行制**
任何视觉/玩法/交互改动，先出**单文件 HTML demo**（双击就能玩/能看），文件名 v1、v2、v3 递增。验收手感通过后才允许进工程。返工发生在 demo 阶段是改一个文件，发生在工程阶段是改十处。

**2. 交付包格式 = 一个 zip + 一份手册.txt**
- zip 内的文件**保持工程目录结构**（`src/pages/xxx.tsx` 原样放进去），Work 只需"按路径复制覆盖"，零思考
- 《手册.txt》用 **Work 的视角**写：编号步骤（复制到哪→跑什么命令→push）、逐项验收清单（可打勾）、回滚方法、已知衔接项和 TODO
- 原则是：Work 全程**不需要翻聊天记录**

**3. 发出前实测**
代码必须在设计方那边 `tsc + vite build` 构建通过，并且用 grep 逐处验证修改真的在文件里（被编辑工具坑过），不把"应该没问题"发出去。

**4. 防覆盖纪律**
共享骨架文件（App.tsx、路由、配置文件这类多方会碰的）**默认不进交付包**，只发"迷你补丁 + 逐行改法"——因为发生过旧版 App.tsx 把 Work 修好的东西覆盖掉的 regression（回归事故）。

**5. 三方分工与沟通格式**
主对话 AI = 总设计师+质检员；Work = 施工队（只执行）；主人 = 甲方。反馈格式是**截图 + 圈出位置 + 说期望效果**；改动攒批做；Work 报错原文带回、禁止自行重试超过 2 次。

**在其他对话中召唤这套方法，直接粘贴这段：**

> 我们要长期协作一个项目，请严格遵守以下【交付协议】：
> ① 视觉/交互/玩法改动，先做单文件 HTML demo（新文件名 v1/v2/v3 递增）给我验收，确认后才进工程；
> ② 每次交付 = 一个 zip（保持工程目录结构）+ 一份给执行 AI 的《手册.txt》（编号步骤/逐项验收清单/回滚方法/已知事项），我会原样转发给执行 AI，它不需要看我们的聊天记录；
> ③ 任何代码发出前，你必须本地构建实测通过，并逐处验证修改真的落在文件里；
> ④ 不要覆盖共享骨架文件（App.tsx/路由/配置），这类改动用迷你补丁包 + 逐行说明；
> ⑤ 我的反馈格式是截图+圈位置+期望效果，改动攒批做；执行层报错原文带回、不得重试超 2 次。
> 如果你理解了，请复述一遍协议，然后我们正式开始。

如果对方复述得对，这套流程就能跨对话复刻。

## 八、案例：zao-chem.com 上线部署流程（2026-09-09 完成，化学网站项目）

把 GitHub 上的网站成品部署到自有服务器（宝塔面板）的完整流程，可直接复用于下次改版上传：

1. **构建变体包**：临时改源码（隐藏互动入口、加「互动社区」外链按钮、换页脚）→ `npm run build` → dist 打 zip → **改完立即 `git checkout --` 还原**，保证仓库主线不被部署变体污染。
2. **宝塔上传**：面板 → 文件 → 站点目录（如 `/www/wwwroot/zao-chem.com/`）→ 上传 zip → 解压覆盖 → 删 zip。面板凭据见《网站备案与部署执行表.xlsx》（**任何密码都不要写进 md/GitHub**）。
3. **伪静态（SPA 回退）**：站点设置 → 伪静态，填 `location / { try_files $uri /index.html; }`（注意不要写 `$uri/`，否则与物理目录同名的路由会 403）。
4. **SSL 证书**：站点设置 → SSL → Let's Encrypt → **勾「全选」**→ 申请 → 开「强制HTTPS」。**踩坑记录**：逐个勾两个域名会只签主域（面板 bug），勾「全选」才能双域名一次签成；申请前若开着强制HTTPS会干扰验证。
5. **验收清单**：http 两域名 301 跳 https、https 两域名 200、SPA 各路由 200、静态页 200、页脚备案号可点击、外链按钮新标签打开。
6. **善后**：ICP 备案号挂页脚（法规强制）；公安联网备案另行办理；旧托管平台（Cloudflare Pages）保留当"排练场"，大改版先在那边预览再传正式服务器。
